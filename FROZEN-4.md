## 0. Target, claim statistic and wording (fixed before any result)

Target: DialBench RPM-10K Acc_eps above the published 62.4 % (MRLM, 8.7 B parameters), official split (`labels/train.json` -> `labels/test.json`, n = 2,000), official scorer. The 62.4 itself was not reproduced; the target is not lowered whatever happens.

- **Unit.** One frozen config (the primary P of section 2) trained from scratch once per seed, each model scored once on the official test by the trainer (EMA weights at the last epoch, window decoder, no checkpoint selection, no test-time augmentation).
- **Headline H** = arithmetic mean of Acc_eps over the valid primary official-split seeds (3 to 5, section 3.3). Never the best seed. Fewer than 3 valid seeds: no headline, the result is reported as incomplete.
- **Governing rule ("clears the target").** The Wilson 95 % interval for a proportion with p = H and n = 2,000 has its lower bound above 62.4 %. That needs **H >= 64.523 %** (1,291 hits of 2,000 = 64.55 % for one model). This is FROZEN-1's Wilson rule applied to the seed mean; seed spread is reported (each seed, min, max, sd) but does not widen the interval.
- **Mandatory qualifier (printed whatever the outcome).** Block bootstrap of the seed-averaged per-image hit: resample the 71 blocks of 160 consecutive image ids (`(image id - 1) // 160` over the 2,000 test names, as `tools/paired_floor.py` and kernel `paired`) with replacement, 5,000 draws, seed 0, 95 % percentile interval. For run 1 this interval was [54.83, 61.62] against Wilson [56.07, 60.39] (half-widths 3.4 and 2.2 points), because test frames come from the same videos. If the half-width stays near 3.4 points, the block lower bound exceeds 62.4 only for H of about 65.8 % or more (the real figure is read from the bootstrap, not from this estimate).
- **Wording, fixed now:**

| Outcome | Allowed wording |
|---|---|
| Wilson lower bound > 62.4 and block lower bound > 62.4 | "Best published result on DialBench RPM-10K, official split, official scorer, self-evaluated, N seeds, as of DATE": H, Wilson, block interval, per-seed values, parameters, size, latency. Plus the standing caveats (62.4 not reproduced; the paper's split and checkpoint selection unknown). |
| Wilson lower bound > 62.4, block lower bound <= 62.4 | "Above the published 62.4 on the point estimate with a Wilson margin (H, Wilson [a, b]); the frame-block interval [c, d] includes 62.4, so the margin is inside the frame-correlation noise of the official split." No "best published" wording. |
| Wilson lower bound <= 62.4 | Negative result (PLAN protocol 6). Section 8 says what is reported. |

- Only the pre-registered primary P carries a claim. The edge pick E and every other config are descriptive; if E alone cleared the rule it is reported as "second of two configs tested, not the pre-registered primary, no claim". The v3 results are organizer baselines with no published number to beat; they never carry a "best published" wording.

## 1. Fixed for every GPU run

- **Code and recipe.** `src/` as at commit `af99342` (last changed in `d9b6e16`; no source edit belongs to this plan): the trainer is the one that produced runs 1 and 2 (`random` seeded in `run()`). Targets, 505 bins, soft labels sigma 0.004, L1 + span-class CE x 0.3, window decoder (half-width 4 bins), augmentation, AdamW with head lr x 3, wd 0.02 and cosine decay are unchanged. Keys not listed in section 2 are the `DEFAULTS` of `src/rpm_train_torch.py`. Only the kernel wrapper (`tools/make_kernel.py` kind `torch-train-gpu`) is new; it adds checks and a start/stop budget and changes nothing the model sees.
- **Precision and hardware.** `amp: true` (fp16 autocast + GradScaler); the trainer uses CUDA only when `amp` is true, so every config must carry it. Machine shape `NvidiaTeslaT4` (Kaggle may attach two T4; the trainer uses one and the second stays idle by design, no sharding). `torch.backends.cudnn.benchmark = True` is set in the wrapper (speed only). GPU runs are not bit-reproducible: seeds fix initialisation, data order and augmentation draws, not cuDNN/atomics.
- **Official-split runs** use `val_mode: "split"`, `n_val: 1000`: the same stratified validation split as run 1 (7,727 training rows, 1,002 held-out rows of which 984 have a determinable range). Reason for "split" instead of the earlier RUNBOOK idea "full": validation stays held out for the validity checks below and for the FROZEN-3 int8 step (under "full" the validation part is empty and the tolerance check would compare against NaN and select nothing), and Stage B then differs from Stage A only by seed and the test look. Cost: 1,002 fewer training rows (11.5 %).
- **v3 runs** use `split_file: "splits_v3.json"`, `split_sha256: "c16e51f6b9bd25cfa9925f19412da2510f9eaad9944dcddfc4d3a261307fc2e3"` (train 7,176; val 945 for monitoring only; test 1,896, of which 1,853 have a determinable range and are scored). The config is the one selected on the OFFICIAL validation; there is no separate v3 selection (as in FROZEN-2).
- **Invalid runs** (decided from the log lines above the TEST line and the validation history, never from a test number): (1) the kernel's `device` line does not show CUDA (the wrapper asserts and exits before any training); (2) for an `npz:` backbone the pre-flight line `PREFLIGHT <arch> missing [...]` is not `missing []` (the trainer loads with `strict=False`, so a key mismatch would silently train from random init; the wrapper asserts); (3) any epoch loss is NaN or inf; (4) the run crashed before its test block or wrote no `_result.json`. An invalid run is not counted, not silently replaced, and is listed in the report with its reason; replacement follows the retry rule (section 7). Every valid run counts, whatever its accuracy.

## 2. Stage A: validation-only selection (kernel `gpu-sweep1`, `run_test: false`, no test image is scored)

Seven candidates in run order (cheapest informative first; the budget guard drops the tail if time runs out). Common to all: `amp true`, `eval_every 5`, `threads 4`, `seed 0`, `val_mode split`, `n_val 1000`, `wd 0.02`. Source of truth: `kernels/gpu-sweep1/configs.json` (committed with this file).

| Tag | Backbone (weights) | Res | bs | lr | Epochs | Warm-up | EMA | Expected min (T4, estimate) |
|---|---|---|---|---|---|---|---|---|
| a1-mnv3s224-f100 | MobileNetV3-small (timm ImageNet) | 224 | 32 | 7e-4 | 100 | 1 | 0.995 | 10 |
| a2-r18-224 | ResNet-18 (npz torchvision ImageNet) | 224 | 64 | 6e-4 | 80 | 2 | 0.995 | 12 |
| a3-r18-320 | ResNet-18 (npz) | 320 | 64 | 6e-4 | 80 | 2 | 0.995 | 24 |

| a7-mnv3l320 | MobileNetV3-large (timm) | 320 | 64 | 8e-4 | 80 | 2 | 0.995 | 16 |

a1 is FROZEN-1's hyperparameters with epochs 30 -> 100 (and amp): "the same config with more compute". The other six cross backbone and input size (the cache holds 224 and 320 px arrays only) at one recipe whose step count (about 9.6k) is near run 1's (7.2k). Learning rates are scaled guesses from run 1's 7e-4 at bs 32; none was tuned. ResNet-34 at 320 is left out on cost (about 45 min per run, too slow to replicate).

**Score** of a candidate = validation Acc_eps of the EMA weights at the final epoch, window decoder, on the 984 scored validation rows (`history[-1].val_ema.window` in `<tag>_result.json`). One standard error is about 1.5 points, so gaps under about 2 points between candidates are noise; the rule is mechanical, it does not claim the winner is truly best.

**Eligible** = valid (section 1), all epochs done, and measured run time T_run <= 30 min, with T_run = sum of the per-epoch `secs` / 60 + 1.5 min (load, evaluation, save).

- **Primary P** = the eligible candidate with the highest score; ties (equal hit count) -> fewer parameters -> earlier in the table.
- **Edge pick E** = among eligible candidates with score >= score(P) - 1.0 percentage point, the one with the fewest parameters (ties -> higher score). If E = P there are no separate edge runs.
- **Futility stop.** If score(P) < 64.0 %, Stage B shrinks to runs R1 to R4 of section 3.2 (P: 3 official seeds + 1 v3 seed) and nothing for E, and no further GPU hours go into the claim. 64.0 % is the level at which, even with zero validation-to-test gap (run 1: 61.28 on validation, 58.25 on test), the test estimate would sit more than half a point under the 64.52 % the rule needs.

## 3. Stage B: final runs (the test looks)

### 3.1 Transformation (exact)
For a selected candidate entry C of `configs.json` (name = tag without its `a<k>-` prefix), the final config entries are C with only these keys changed or added:
- official: `seed: s`, `run_test: true`, `tag: "f-<name>-off-s<s>"` (`val_mode`, `n_val` stay as in C);
- v3: `seed: s`, `run_test: true`, `split_file: "splits_v3.json"`, `split_sha256: "c16e51f6b9bd25cfa9925f19412da2510f9eaad9944dcddfc4d3a261307fc2e3"`, `tag: "f-<name>-v3-s<s>"`.
Every other key (arch, pretrained, res, bs, lr, epochs, warmup_epochs, ema, wd, amp, eval_every, threads) is copied unchanged. No hyperparameter is changed between Stage A and Stage B.

### 3.2 Run list in priority order
R1 P-off s0, R2 P-off s1, R3 P-off s2, R4 P-v3 s0, R5 P-off s3, R6 P-off s4, R7 E-off s0, R8 E-v3 s0, R9 P-v3 s1, R10 P-v3 s2, R11 E-off s1, R12 E-off s2. (If E = P, delete R7, R8, R11, R12.) Seeds are the integers named here, fixed now.

### 3.3 Budget rule that decides how many runs are made
Charge of a run = T_run (section 2, measured in Stage A) of its candidate, rounded up to whole minutes. Stage B budget = **200 run-minutes**. Walk the list from R1; keep a run while the running total of charges stays <= 200; stop at the first run that does not fit (no skipping ahead). Examples: T_run 15 min for P and E -> all 12 runs; T_run 25 min -> R1 to R8 (P: 5 official + 1 v3 seed, E: 1 official + 1 v3 seed). The headline H uses all kept valid P official runs (3 to 5).

### 3.4 Kernels and caps
`gpu-final-off` = the kept official runs in list order; `gpu-final-v3` = the kept v3 runs in list order (sources add `rpm-split3`). Both are built with `tools/make_kernel.py ... torch-train-gpu`. For a kernel with charges summing to S seconds: `-t` cap = 300 * ceil((600 + 1.2 * S) / 300) s, in-script start/stop budget = cap - 900 s, per-run expected seconds = charge * 60. Stage A: `-t 9000`, budget 8100 s (expected 6,930 s).

### 3.5 Addendum S (written after Stage A, committed before any Stage B push)
Contents: the Stage A table (score, params, T_run, validity per candidate), P, E, whether the futility stop applies, the kept run list with charges, the caps, and the sha256 of both Stage B `script.py` files. Writing and committing Addendum S is a hard precondition of every Stage B push. Do not chain GPU kernels (`logs/chain/*.next` pushes the next kernel without that commit).

## 7. Retry and stop rules
- One retry per failed kernel, inside the 8 h cap, only for a fix that changes no pre-registered setting (a typo, a path, an infrastructure failure). The fix and the reason are committed as an amendment to this file before the re-push. A retry that would take the program past 8 GPU-h needs the owner's yes. A retry never replaces a valid result.
- `locks/kaggle-gpu` is shared with gas and small-lm; hold it for the whole session and log every session in `RESOURCES.md`.
- Stop a session (web UI; kaggle 2.2.4 has no cancel command) when the 5-minute log check shows no CUDA device, `missing` not empty, or a first-epoch time more than 3 x the estimate.

## 8. What is reported if the target is missed
The target stays 62.4. `SUBMISSION.md` section 0 and the report give: H with every seed's value, the Wilson and block intervals, and the verdict of the table in section 0; P's parameters, ONNX sizes (fp32 and the selected int8) and latency; the improvement over run 1 (58.25 %, one seed) described only as far as the seed spread and the block interval support; the whole Stage A table including the continuity row a1; the v3 organizer baseline of P with its copy floor (34.1 %) and the 14-block interval; E's numbers; the number of GPU hours used. Unused quota is not spent on chasing the claim. Any next step (resolutions above 320, a different head, a larger model, more data) needs a new pre-registration and the owner's yes.
